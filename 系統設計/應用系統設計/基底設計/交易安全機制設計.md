## 一、設計目的

本系統採用 **雙重令牌驗證機制** (Session ID + Transaction Token),確保 API 交易的安全性,防範未授權的 API 呼叫。

### 1.1 設計目標

- ✅ 防止手動 API 呼叫攻擊
- ✅ 確保交易的時效性 (15 分鐘限制)
- ✅ 綁定 Session 與 Token,防止令牌濫用
- ✅ 支援功能級別的權限控制
- ✅ 提供一次性使用選項
- ✅ 支援高並發與分散式部署

### 1.2 核心設計理念

```
Token 綁定 session_id (而非 user_id)
Session_id 綁定 user_id
驗證時雙重檢查 session_id 和 token
```

## 二、架構設計

### 2.1 整體架構

```
┌──────────────┐
│   使用者      │
└──────┬───────┘
       │ 1. 登入
       ▼
┌──────────────┐
│  認證 API    │ → 產生 Session ID (JWT Token)
│              │ → 儲存 Session 資訊到 Redis
└──────┬───────┘
       │
       │ 2. 進入功能頁面
       │    帶著 Session ID
       ▼
┌──────────────┐
│  申請 Token  │ → 驗證 Session ID
│   API        │ → 檢查功能權限
│              │ → 生成 Transaction Token
│              │ → Token 綁定 Session ID
│              │ → 儲存到 Redis (TTL 15分鐘)
└──────┬───────┘
       │
       │ 3. 執行操作
       │    帶著 Session ID + Transaction Token
       ▼
┌──────────────┐
│  業務 API    │ → 驗證 Session ID (取得 user_id)
│              │ → 驗證 Transaction Token
│              │ → 檢查 Token 是否綁定此 Session
│              │ → 檢查功能代碼是否匹配
│              │ → 檢查是否過期
│              │ → 執行業務邏輯
└──────────────┘
```

### 2.2 資料儲存架構 (Redis)

```
Redis 資料結構:

1. Token 資訊
   Key: txn_token:<token_hash>
   Value: {
     "session_id": "<jwt_token>",
     "func_code": "role_rights",
     "created_at": "2026-01-24T04:00:00Z",
     "used": false
   }
   TTL: 900 秒 (15 分鐘)

2. Session 的所有 Tokens
   Key: session_tokens:<session_id>
   Type: Set
   Members: [<token1>, <token2>, ...]
   TTL: 900 秒

   用途:
   - 使用者登出時批量撤銷所有 token
   - Session 過期時自動清理所有相關 token
```

## 三、核心流程

### 3.1 使用者登入流程

```
POST /api/auth/login
Request: {
  "username": "user@example.com",
  "password": "password"
}

Response: {
  "access_token": "<jwt_token>",  // Session ID
  "token_type": "bearer",
  "expires_in": 86400  // 24小時
}

後端處理:
1. 驗證帳號密碼
2. 生成 JWT Token (包含 user_id, username, roles)
3. (可選) 將 Session 資訊儲存到 Redis
4. 回傳 Session ID
```

### 3.2 申請交易令牌流程

```
POST /api/transaction/request
Headers: {
  "Authorization": "Bearer <session_id>"
}
Request: {
  "func_code": "role_rights"
}

Response: {
  "txn_token": "abc123...",
  "expires_in": 900,
  "func_code": "role_rights",
  "permissions": {
    "create": false,
    "read": true,
    "update": false,
    "delete": false,
    "print": false,
    "file": false
  }
}

後端處理:
1. 驗證 Session ID (JWT) → 取得 user_id
2. 檢查使用者對該功能的權限
3. 生成 Transaction Token:
   - Token 綁定 session_id (不是 user_id!)
   - Token 綁定 func_code
4. 儲存到 Redis:
   - txn_token:<hash> → token 資訊 (TTL 15分鐘)
   - session_tokens:<session_id> → 將 token 加入集合
5. 回傳 token 和權限資訊
```

### 3.3 執行業務操作流程

```
POST /api/role_rights/6/save
Headers: {
  "Authorization": "Bearer <session_id>",
  "X-Txn-Token": "<txn_token>"
}
Request: {
  "rights": [...]
}

後端處理:
1. 驗證 Session ID → 取得 user_id 和 session_id
2. 驗證 Transaction Token:
   a. Token 是否存在? (從 Redis 查詢)
   b. Token 是否過期? (Redis TTL)
   c. ★ Token 的 session_id 是否匹配?
   d. Token 的 func_code 是否匹配?
   e. Token 是否已使用? (如果是一次性)
3. 權限檢查:
   - 檢查使用者是否有 update 權限
4. 執行業務邏輯
5. (可選) 銷毀 token (如果是一次性使用)
```

### 3.4 使用者登出流程

```
POST /api/auth/logout
Headers: {
  "Authorization": "Bearer <session_id>"
}

後端處理:
1. 撤銷此 session 的所有 tokens:
   - 從 session_tokens:<session_id> 取得所有 tokens
   - 逐一刪除 txn_token:<hash>
   - 刪除 session_tokens:<session_id> 集合
2. 將 JWT 加入黑名單 (可選)
3. 回傳成功訊息
```

## 四、安全機制

### 4.1 防範手動 API 呼叫

**攻擊情境 1**: 攻擊者竊取 Session ID

```bash
curl -X POST http://api.example.com/api/role_rights/6/save \
  -H "Authorization: Bearer <stolen_session_id>" \
  -d '{"rights": [...]}'
```

**防禦結果**: ❌ 失敗
- 缺少 `X-Txn-Token` header
- 後端回傳: `401 Unauthorized: Missing transaction token`

---

**攻擊情境 2**: 攻擊者同時竊取 Session ID 和 Token

```bash
curl -X POST http://api.example.com/api/role_rights/6/save \
  -H "Authorization: Bearer <stolen_session_id>" \
  -H "X-Txn-Token: <stolen_token>" \
  -d '{"rights": [...]}'
```

**防禦結果**:
- 如果在 15 分鐘內: ⚠️ 可能成功 (但有日誌記錄)
- 如果超過 15 分鐘: ❌ Token 已過期
- 如果是一次性 token: ❌ Token 已使用

---

**攻擊情境 3**: 攻擊者使用別的 Session 的 Token

攻擊者有 Session A,但竊取了 Session B 的 Token:

```bash
curl -X POST http://api.example.com/api/role_rights/6/save \
  -H "Authorization: Bearer <session_A>" \
  -H "X-Txn-Token: <session_B_token>" \
  -d '{"rights": [...]}'
```

**防禦結果**: ❌ 失敗
- Token 的 session_id 與請求的 Session ID 不符
- 後端回傳: `403 Forbidden: Transaction token mismatch`

### 4.2 時間限制機制

| 項目 | 時效 | 說明 |
|-----|------|------|
| Session ID (JWT) | 24 小時 | 使用者登入狀態 |
| Transaction Token | 15 分鐘 | 功能操作權限 |
| Token 自動清理 | Redis TTL | 過期自動刪除 |

### 4.3 一次性使用機制

```python
# 關鍵操作使用一次性 token
@router.delete("/users/{user_id}")
async def delete_user(
    user_id: int,
    _: None = Depends(require_txn_token("users", "delete", one_time_use=True))
):
    # Token 驗證後立即銷毀
    # 攻擊者無法重複使用
    ...
```

### 4.4 功能綁定機制

```
Token A (綁定 "role_rights")
  → 只能用於 role_rights 相關 API
  → 不能用於 organizations API
  → 不能用於 users API

Token B (綁定 "users")
  → 只能用於 users 相關 API
```

## 五、實作細節

### 5.1 Token 生成演算法

```python
import secrets
import hashlib
from datetime import datetime

def generate_txn_token(session_id: str, func_code: str):
    # 1. 生成隨機字串
    random_str = secrets.token_urlsafe(32)

    # 2. 組合資料
    token_data = f"{session_id}:{func_code}:{random_str}:{datetime.utcnow().isoformat()}"

    # 3. SHA-256 雜湊
    txn_token = hashlib.sha256(token_data.encode()).hexdigest()

    return txn_token
```

### 5.2 Redis 儲存結構

```python
# 儲存 token 資訊
redis_client.setex(
    name=f"txn_token:{txn_token}",
    time=900,  # 15 分鐘
    value=json.dumps({
        "session_id": session_id,
        "func_code": func_code,
        "created_at": datetime.utcnow().isoformat(),
        "used": False
    })
)

# 記錄 session 的所有 tokens
redis_client.sadd(f"session_tokens:{session_id}", txn_token)
redis_client.expire(f"session_tokens:{session_id}", 900)
```

### 5.3 Token 驗證邏輯

```python
def verify_txn_token(txn_token: str, session_id: str, func_code: str):
    # 1. 從 Redis 取得 token 資訊
    token_data = redis_client.get(f"txn_token:{txn_token}")

    if not token_data:
        raise HTTPException(401, "Token 不存在或已過期")

    token_info = json.loads(token_data)

    # 2. 檢查 session_id 是否匹配
    if token_info["session_id"] != session_id:
        raise HTTPException(403, "Token 與 Session 不符")

    # 3. 檢查 func_code 是否匹配
    if token_info["func_code"] != func_code:
        raise HTTPException(403, "Token 與功能代碼不符")

    # 4. 檢查是否已使用 (一次性)
    if one_time_use and token_info["used"]:
        raise HTTPException(401, "Token 已使用")

    return True
```

## 六、前端實作

### 6.1 使用 Hook 管理 Token

```typescript
import { useTransactionToken } from '../hooks/useTransactionToken';

const RoleRightsPage = () => {
  // 自動申請 token
  const { txnToken, permissions, remainingSeconds } =
    useTransactionToken('role_rights');

  // 根據權限控制 UI
  const canUpdate = permissions?.update || false;

  // 執行操作時帶上 token
  const handleSave = async () => {
    await saveRoleRights(data, txnToken);
  };

  return (
    <div>
      {remainingSeconds < 60 && (
        <Warning>令牌即將過期,請盡快完成操作</Warning>
      )}
      <button disabled={!canUpdate} onClick={handleSave}>
        儲存
      </button>
    </div>
  );
};
```

### 6.2 Service 層帶上 Token

```typescript
import axios from '../api/axios';

export const saveRoleRights = async (
  data: any,
  txnToken: string
) => {
  const response = await axios.post(
    '/api/role_rights/save',
    data,
    {
      headers: {
        'X-Txn-Token': txnToken
      }
    }
  );
  return response.data;
};
```

## 十一、常見問題

### Q: 為什麼 Token 綁定 session_id 而不是 user_id?

A:
1. Session 過期時,所有相關 token 自動失效
2. 使用者登出時,可批量撤銷所有 token
3. 更符合 session 機制的設計理念
4. 防止 token 跨 session 使用

### Q: 如果 Redis 故障怎麼辦?

A: 系統會自動回退到記憶體儲存,但有以下限制:
- 不支援分散式部署
- 伺服器重啟後 token 消失
- 建議生產環境使用 Redis Cluster

### Q: Token 可以續期嗎?

A: 不建議續期,建議重新申請:
1. 確保時效性
2. 避免長期有效的 token
3. 更簡單的實作邏輯

### Q: 可以同時開多個功能頁面嗎?

A: 可以,每個功能有獨立的 token,互不影響。
